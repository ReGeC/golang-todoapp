# Правила комментариев

В проекте предпочтительны маленькие функции и говорящие имена. Комментарии
нужны там, где они объясняют контракт, инвариант или неочевидное решение.
Комментарии, которые пересказывают код, добавлять не нужно.

## Где комментарии полезны

### Package-level документация

Стоит добавить `doc.go` или короткий комментарий к package, если пакет задает
правила для других частей системы:

- `internal/core/domain` - доменные инварианты;
- `internal/core/transport/http/types` - nullable JSON semantics;
- `internal/core/transport/http/response` - mapping ошибок в HTTP-статусы;
- `internal/core/transport/http/middleware` - назначение middleware;
- `internal/core/repository/postgres/pool` - минимальный контракт DB pool.

### Неочевидные бизнес-правила

Комментарии уместны рядом с правилами:

- `completed` и `completed_at` должны изменяться согласованно;
- PATCH использует three-state logic;
- `version` используется для optimistic locking;
- статистика считает average только по завершенным задачам.

### Инфраструктурные решения

Комментарии полезны там, где поведение не очевидно по одной строке:

- почему API router оборачивается в `http.StripPrefix`;
- почему response writer хранит uninitialized status;
- почему request id пишется и в request, и в response;
- почему repository создает context with timeout на каждую операцию.

## Где комментарии избыточны

Не стоит комментировать:

- простые конструкторы `New...`;
- очевидные DTO struct fields, если они уже описаны json tags и Swagger;
- прямолинейные CRUD handler methods;
- `Scan` полей из SQL в model struct;
- model-to-domain mapping;
- service methods, которые только вызывают `Validate` и repository;
- импорты и очевидные локальные переменные.

Плохой пример:

```go
// Create user creates user.
func (s *UsersService) CreateUser(...) ...
```

Такой комментарий не добавляет знания.

## Swagger-комментарии

Swagger-аннотации уже являются API-документацией. Их нужно поддерживать
актуальными, но не превращать в подробный tutorial.

Хороший Swagger-комментарий должен фиксировать:

- назначение endpoint;
- обязательные path/query/body параметры;
- успешные и ошибочные статусы;
- важные особенности контракта, например nullable PATCH.

## Документация вместо комментариев

Если объяснение занимает больше нескольких строк и относится не к конкретному
месту в коде, лучше вынести его в `docs/*.md`.

Примеры:

- общая архитектура;
- процесс локального запуска;
- стратегия тестирования;
- правила добавления новой фичи;
- описание схемы БД.

## Рекомендуемый порядок

1. Сначала обновлять внешнюю документацию в `docs/*.md`.
2. Затем добавлять короткие package-level комментарии для общих пакетов.
3. Затем точечно комментировать только неочевидные места.
4. Не добавлять комментарии в CRUD-код без конкретной причины.
